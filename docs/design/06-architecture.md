# 06. 기술 아키텍처 — 모듈 · 서버 · 클라이언트

## 1. 기술 선택

| 영역 | 선택 | 이유 |
| --- | --- | --- |
| 언어 | TypeScript (strict) | 서버·클라이언트가 같은 규칙 코드를 공유 |
| 렌더링 | 자체 Canvas2D 픽셀 엔진 | 640×360 논리 해상도에서 픽셀 단위 제어, 의존성 최소화 |
| 빌드 | Vite (클라이언트), tsc (core/server) | 빠른 개발 서버, 워커 번들링 |
| 테스트 | Vitest | core 규칙 단위 테스트 |
| 데스크톱 | Electron + steamworks.js | 스팀 업적·클라우드 세이브·오버레이 |
| 멀티플레이 | WebSocket(ws) 전용 서버 | 같은 GameServer 코드를 Node에서 실행 |
| 폰트 | Galmuri (OFL) | 한글 픽셀 폰트 |

## 2. 패키지 구조 (npm workspaces 모노레포)

```
packages/
├─ core/     @lumina/core     순수 규칙·데이터. DOM·Node API 사용 금지. 결정론적.
│  ├─ data/        작물 200종, 아이템, 상점 품목
│  ├─ math/        시드 난수, 노이즈
│  ├─ time/        달력·시계
│  ├─ weather/     기후(기온), 날씨 생성
│  ├─ world/       타일 정의, 섬 생성기, 충돌, 길찾기
│  ├─ farming/     토양·작물 생장·품질·스프링클러
│  ├─ economy/     가격·시세·출하 정산
│  ├─ inventory/   인벤토리 슬롯·스택
│  ├─ player/      외형(커스터마이즈) 정의
│  ├─ state/       월드 상태 타입, 세이브 스키마·마이그레이션
│  └─ protocol/    클라이언트↔서버 메시지 타입
│
├─ server/   @lumina/server   권한 있는(authoritative) 시뮬레이션
│  ├─ GameServer.ts        세션·틱·메시지 처리의 중심
│  ├─ handlers/            메시지별 처리(도구, 상호작용, 구매, 포장, 적재…)
│  ├─ systems/             시간 진행, 일일 정산, 출항
│  ├─ persistence/         SaveStore 인터페이스(메모리/파일/IndexedDB)
│  ├─ worker/              브라우저 Web Worker 진입점(싱글플레이 내장 서버)
│  └─ node/                Node WebSocket 전용 서버 진입점(멀티플레이)
│
└─ client/   @lumina/client   보여주기·입력·사운드. 규칙을 결정하지 않음
   ├─ engine/     게임 루프, 픽셀 캔버스, 입력, 카메라, 씬 관리, 트윈
   ├─ art/        팔레트, 절차적 픽셀 스프라이트 생성기(타일·작물·캐릭터·건물)
   ├─ render/     월드 청크 렌더러, 물·거품, 오브젝트 Y정렬, 조명, 날씨 효과
   ├─ ui/         항해 일지 UI 위젯(하늘 다이얼, 핫바, 일지, 상점, 포장대…)
   ├─ audio/      WebAudio 절차적 앰비언스·효과음·음악
   ├─ net/        Connection(Worker / WebSocket) 추상화, 클라이언트 월드 미러
   └─ scenes/     타이틀, 캐릭터 만들기, 게임 플레이
apps/
└─ desktop/  Electron 셸 + 스팀 연동 (M4 단계)
```

### 의존 방향 (단방향)
```
client ──▶ core ◀── server
client ──▶ server/worker (싱글플레이일 때 워커 번들만)
```
- core는 아무것도 의존하지 않는다. server와 client는 서로의 내부를 모른다.
- 둘은 **protocol 메시지**로만 대화한다.

## 3. 싱글플레이 = 내장 서버

```
┌──────────── 브라우저 / Electron ────────────┐
│  메인 스레드: client                          │
│    Input → Intent 메시지 ─┐                  │
│    Render ← 상태 미러 ◀──┤ postMessage      │
│  Web Worker: server      │                  │
│    GameServer ◀──────────┘                  │
│    SaveStore(IndexedDB)                     │
└─────────────────────────────────────────────┘
```
- 시뮬레이션이 워커에서 돌아 렌더링 프레임을 방해하지 않는다.
- 멀티플레이는 같은 `GameServer`를 Node에서 돌리고 연결만 WebSocket으로 바꾼다.

## 4. 네트워크 모델

- **서버 권한**: 도구 사용, 수확, 구매, 포장, 적재, 시간, 날씨, 작물 생장은 모두 서버가 결정.
- **이동은 클라이언트 예측**: 클라이언트가 충돌 판정 후 위치를 20Hz로 보내고, 서버는 최대 속도
  검증만 한다(협동 게임 특성상 충분).
- 클라이언트는 서버 응답 전에 도구 애니메이션을 먼저 재생해 입력 지연을 숨긴다.
- **월드 전송 최소화**: 섬 지형은 시드로부터 core 생성기가 양쪽에서 똑같이 만든다.
  서버는 시드와 변하는 부분(밭 타일·작물·설치물)만 보낸다.

### 주요 메시지 (`core/src/protocol`)
| 방향 | 메시지 | 내용 |
| --- | --- | --- |
| C→S | `join` | 세이브 슬롯, (새 게임이면) 캐릭터 외형·이름·농장 이름 |
| C→S | `move` | 위치, 방향, 걷는 중 여부 |
| C→S | `useItem` | 핫바 칸, 대상 타일 |
| C→S | `interact` | 대상 타일(상점·배·포장대·집·수확) |
| C→S | `buy` / `pack` / `loadShip` / `sleep` / `swapSlots` | 각 행동 |
| S→C | `welcome` | 플레이어 ID, 월드 시드, 전체 동적 상태 |
| S→C | `tick` | 시간·날씨·다른 플레이어 위치 (5Hz) |
| S→C | `tiles` | 변경된 밭 타일 목록 |
| S→C | `self` | 내 인벤토리·돈·체력·들고 있는 상자 |
| S→C | `notice` | 토스트/편지/출항/하루 정산 이벤트 |

## 5. 상태와 저장

- `WorldState` = { 시드, 시계, 오늘/내일 날씨, 밭 타일 맵, 설치물, 배 적재 목록, 시세, 플레이어들 }
- JSON 직렬화 가능한 순수 데이터만. 세이브 = `{ version, savedAt, state }`.
- `migrateSave(v)`로 구버전 세이브를 최신 구조로 변환.

## 6. 렌더링 파이프라인 (한 프레임)

```
1. 물 베이스(청크 캐시) + 해안 거품 애니메이션 프레임 + 반짝임
2. 지형 청크(16×16타일=256px 캔버스, 화면에 보일 때 생성·LRU 캐시)
3. 밭 타일(갈린 흙·젖은 흙·비료) — 동적
4. Y정렬 오브젝트: 나무, 건물, 작물, 캐릭터, 소품, 배
5. 구름 그림자 (곱하기)
6. 날씨 입자: 비·눈·꽃잎·낙엽, 빗방울 튐
7. 조명: 시간대 색보정(곱하기) + 광원 글로우(가산) + 등대 빛줄기
8. 안개 레이어, 번개 섬광
9. UI (같은 논리 해상도, 픽셀 텍스트 캐시)
10. 정수 배율로 화면 캔버스에 확대 출력
```

## 7. 코드 규칙

- core 함수는 입력 → 출력의 순수 함수 위주, 난수는 항상 시드 RNG를 인자로 받는다.
- 게임 수치는 코드에 흩지 말고 core의 상수·데이터 테이블에 둔다.
- 새 기능 = core 규칙(+테스트) → server 핸들러 → client 표현 순서로 추가.
- `npm run check`(타입체크 + 테스트)가 통과해야 커밋.
